Documentación del proyecto · v0.1

Contexto útil, guardado cerca del trabajo.

Agent Memory es una memoria local, trazable y controlada por proyecto para agentes. Conserva decisiones y aprendizajes entre sesiones sin depender de un servicio remoto.

SQLite + FTS5MCP por stdioWindows x64Linux x64Go sin cgo

Qué resuelve

Una sesión de agente termina, pero sus decisiones no deberían desaparecer. Agent Memory ofrece una superficie pequeña para recuperar conocimiento relevante, guardar información durable y mantener el ciclo de vida de cada entrada bajo control.

Local-first

Datos en el checkout

La base SQLite se guarda en .ytk-memory/. El uso cotidiano no requiere red, una base externa ni credenciales corporativas.

Aislada

Scope por proyecto

Cada proceso MCP queda fijado a un proyecto y a una base. Las búsquedas, lecturas y sesiones no cruzan workspaces.

Operable

Diagnóstico y recuperación

doctor, backups, upgrade y rollback hacen visible el estado y evitan reemplazos silenciosos de la base.

Arquitectura

El host del agente sólo conoce herramientas MCP. El binario resuelve validación, ownership, persistencia y lifecycle; SQLite conserva los datos.

Qué información se guarda

La memoria está pensada para conocimiento reutilizable y breve. Cada registro tiene identidad, tipo, contenido, scope y fechas que permiten saber si sigue vigente.

Entidad Contenido Uso
Sesión Identificador, proyecto, owner, inicio, cierre y resumen. Vincula el trabajo de una interacción y evita que otro proceso cierre la sesión.
Memory item Tipo, título, contenido, subjectKey, tags, estado y vigencia. Representa una decisión, hallazgo, patrón, preferencia o resumen reutilizable.
Relación Origen, destino, tipo y fecha. Expresa que una memoria apoya, contradice, reemplaza o se relaciona con otra.
Metadata Fuente, área, fechas de revisión y expiración. Permite filtrar, auditar y retirar contexto vencido sin borrar todo el historial.
Regla de contenido: no guardes secretos, tokens, contraseñas, credenciales, transcripciones completas ni datos personales innecesarios. El runtime rechaza contenido sensible antes de persistirlo.

Tipos admitidos

decision · discovery · pattern · preference · summary

Cómo usa la memoria un agente

1. Abrir sesión
2. Buscar contexto
3. Decidir
4. Guardar aprendizaje
5. Cerrar y resumir

El protocolo recomienda recuperar contexto antes de una decisión técnica, tratar los resultados como evidencia y guardar sólo aquello que otra sesión pueda reutilizar. El agente usa un subjectKey estable para actualizar un tema sin duplicarlo. 

// Inicio y recall
> memory_session_start({ "query": "decisiones sobre autenticación", "limit": 10 })

// Aprendizaje durable
> memory_save({
    "type": "decision",
    "title": "Usar tokens de corta duración",
    "content": "La API valida ...",
    "subjectKey": "security/token-lifetime",
    "tags": ["security", "api"]
  })

// Cierre
> memory_session_finish({ "sessionId": "...", "summary": "..." })

El cierre puede crear automáticamente un registro de tipo summary. Los ítems tienen estados active, needs_review, superseded y archived; una entrada archivada no vuelve a aparecer en la búsqueda normal.

MCP y tools

El servidor usa MCP sobre stdio. El host inicia un proceso del binario y se comunica mediante mensajes JSON-RPC. La salida estándar queda reservada para MCP.

Tool Entrada principal Respuesta
memory_session_start query?, limit?, maxChars? sessionId y entradas recuperadas opcionales.
memory_search query, limit?, maxChars? Entradas activas del proyecto, ordenadas por relevancia FTS5.
memory_get memoryId, maxChars? Una entrada completa, respetando proyecto y área.
memory_save type, title, content, subjectKey?, tags, fuente y sesión. stored y entryId; un topic existente se actualiza.
memory_session_finish sessionId, summary? Confirmación de cierre y summaryStored.

Límites útiles

Las búsquedas aceptan hasta 100 resultados y 20.000 caracteres por entrada. Los títulos admiten 500 caracteres y el contenido durable hasta 50.000.

Seguridad de scope

El proceso conserva un owner aleatorio para sus sesiones. Una lectura por ID fuera del proyecto se presenta como inexistente, evitando filtraciones de existencia.

Instalación desde un repositorio

Descargá un artefacto aprobado para tu plataforma, verificá su hash y firma, agregá el binario al PATH y ejecutá el setup desde la raíz del checkout. 

# Verificar disponibilidad
ytk-memory --version

# Revisar cambios
ytk-memory setup codex --dry-run

# Aplicar configuración
ytk-memory setup codex

# Verificar base, registro MCP y ejecutable
ytk-memory doctor
Resultado: se crea .ytk-memory/ytk-memory.sqlite, se registra el servidor en CODEX_HOME/config.toml y se instalan instrucciones locales administradas. Reiniciá el host MCP para que cargue la configuración.

Configuración

Ubicación Uso
CODEX_HOME/config.toml Registro MCP global y genérico de Codex.
Repositorio actual Instrucciones en AGENTS.md y skill local.
--portable También genera .ytk-memory/mcp.json para hosts portables.

Setup, verificación y mantenimiento

# Backup consistente
ytk-memory backup --to .ytk-memory/backup.sqlite

# Upgrade con backup obligatorio
ytk-memory upgrade --backup-to .ytk-memory/pre-upgrade.sqlite

# Rollback confirmado y protegido
ytk-memory rollback   --from .ytk-memory/pre-upgrade.sqlite   --backup-current-to .ytk-memory/current.sqlite   --confirm

# Retirar sólo la integración administrada
ytk-memory uninstall codex

doctor comprueba que la base sea legible y que el registro MCP global esté disponible y que el proyecto tenga una configuración local válida. Los destinos de backup existentes se rechazan salvo que se indique --overwrite.

Configuración creada

.ytk-memory.json, CODEX_HOME/config.toml, AGENTS.md, .agents/skills/ytk-memory/SKILL.md y, opcionalmente, .ytk-memory/mcp.json.

Reversibilidad

El desinstalador quita la activación local y conserva la base, los backups y el MCP global. En una terminal ofrece quitar también el registro global.

Decisiones de diseño

SQLite

Local y portable

Reduce dependencias operativas, permite backup simple y mantiene la memoria cerca del código que la necesita.

FTS5

Recall explicable

La búsqueda léxica es rápida, auditable y adecuada para decisiones, nombres de módulos y términos de proyecto.

MCP

Superficie pequeña

Un conjunto de cinco herramientas permite integrar distintos hosts sin acoplar el Core a una interfaz de usuario.

  • Sin cgo: el binario usa SQLite embebido y se distribuye sin toolchain nativo.
  • Scope explícito: proyecto, base y área viajan en la configuración del proceso.
  • Idempotencia: subjectKey actualiza conocimiento en lugar de multiplicarlo.
  • Lifecycle: vigencia, revisión y archivado evitan que contexto obsoleto contamine una respuesta.
  • Operaciones seguras: backup antes de upgrade y copia de seguridad durante rollback.

Fortalezas y puntos a mejorar

Fortalezas
  • Instalación local sin servicios externos.
  • Paridad de contrato MCP y respuestas estructuradas.
  • Aislamiento por proyecto y owner de sesión.
  • Datos inspeccionables y backups verificables.
  • Distribución nativa con hash y firma.
  • Pruebas de conformance, superficie y release.
A mejorar
  • Validar el canal interno de releases con una clave estable y revocación.
  • Medir recall y latencia con corpus de trabajo representativo.
  • Añadir identidad corporativa cuando el uso multiusuario lo requiera.
  • Evaluar stemming o retrieval semántico sin perder explicabilidad.
  • Incorporar macOS arm64 después de una validación nativa equivalente.

Posibilidades de crecimiento

Más hosts

El manifiesto portable permite conectar otros hosts MCP manteniendo las mismas tools y el mismo scope.

Mejor recuperación

Se pueden sumar mejoras de recuperación léxica y sincronización futura cuando el producto lo requiera.

Gobernanza

Auditoría, políticas de retención, sincronización selectiva y autorización corporativa pueden crecer sin cambiar el contrato base.
